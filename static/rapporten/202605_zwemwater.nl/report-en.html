01 On all pages

#1 - Keyboard focus moves outside the dialog

Impact: High Type: Technical WCAG: 2.4.3 EN: 9.2.4.3

When a visitor visits the website for the first time, a cookie dialog appears. Right now, the keyboard focus can escape the open dialog and move to the underlying page content. As long as the dialog is open, the keyboard focus should stay within the dialog.

User story

As a visitor, I use the website with a keyboard and a screen reader. When a dialog is open and I press Tab, I end up on the page behind it. I expect the focus to stay within the dialog until I close it.

How to test

Tab from top to bottom through the page and watch for jumps that do not match the visual order. Open every dialog, every dropdown, and every dynamic component and check whether the focus lands in a logical place. Avoid positive tabindex values entirely.

Solution

This can be achieved with JavaScript by trapping the focus within the dialog until it is closed (by clicking a close button or pressing Escape). An alternative is for the dialog to close automatically when the focus tries to leave it.

#2 - Keyboard focus is obscured by the dialog

Impact: High Type: Technical WCAG: 2.4.11 EN: 9.2.4.11

When a visitor visits the website for the first time, a cookie dialog appears. This dialog covers part of the page. Interactive elements beneath this dialog can still receive keyboard focus, even though they are visually covered.

User story

As a visitor, I use the website with a keyboard. When I press Tab to navigate through the page, I sometimes land on an element I cannot see. I expect only visible elements to receive keyboard focus.

How to test

Tab through the page while sticky headers, footers, cookie banners, and chat widgets are visible. At each step, at least part of the focused element with its focus indicator should be visible, never fully hidden behind other content.

Solution

Only visible elements should be able to receive keyboard focus.

#3 - Heading does not have the correct markup

Impact: Medium Type: Technical WCAG: 1.3.1 EN: 9.1.3.1

The cookie dialog contains the text "Deze website maakt gebruik van cookies" that looks like a heading. This text is marked up with an h2 element, but it also receives role="status", which overrides the heading semantics. As a result, a screen reader does not announce the text as a heading. A status role is intended for live announcements of dynamic changes, not for a static title.

When text functions as a heading but lacks the correct markup, it loses its semantic meaning and becomes inaccessible to visitors who rely on assistive technology such as screen readers. Headings are essential for navigating the content and understanding its structure.

User story

As a visitor, I read the website with a screen reader. When I navigate through the page or a dialog by heading, I expect all visible headings to be recognized and announced as headings. That way I understand the structure of the content and navigate quickly between sections.

How to test

Open the cookie dialog and navigate through it using a screen reader's heading navigation or heading list. Check whether the text "Deze website maakt gebruik van cookies" is announced as a heading and appears in the heading list. Inspect the accessibility information and confirm that the element has heading semantics that are not overridden by another role.

Solution

Make sure "Deze website maakt gebruik van cookies" is exposed to assistive technology as a heading. Remove role="status" from the heading element, because status roles are intended for dynamic announcements and override the heading semantics.

#4 - Not all of the logo's visible text is in the text alternative

Impact: High Type: Content WCAG: 1.1.1, 2.5.3 EN: 9.1.1.1, 9.2.5.3

The logo at the top of the website shows the full text "Zwemwater.nl Zwemmen in natuurwater. Waar is het schoon en veilig", but the text alternative (the alt text) is "Logo:Zwemwater.nl Zwemmen in natuurwater. Waar is het schoon". The alt text should contain all visible text in the logo, including the words "en veilig", so that visitors who cannot see the image receive the same information.

User story

As a visitor, I read the website with a screen reader. When I navigate to the logo, I do not hear the organization's full name. I expect the text I hear to match what is shown visually in the logo.

How to test

Inspect every image, icon, and SVG in DevTools. Informative ones need an alt (or accessible name) that conveys the meaning; decorative ones use alt="" or aria-hidden="true". Check with a screen reader that no noise (file name, "image") is announced.

Solution

Update the text alternative so that it contains the logo's full visible text. Because this logo is a link, the word "Logo" can be left out.

#5 - Expandable menu item and submenu are built with an incorrect ARIA structure

Impact: High Type: Technical WCAG: 4.1.2 EN: 9.4.1.2

In the main navigation menu, the menu item "Over ons" contains an expandable submenu. Both the expandable menu item and the submenu it opens are built incorrectly.

The role="menuitem" and the attributes aria-haspopup and aria-expanded are on the li element, while the actual interactive element is the nested a element. The li element is not focusable, and the focusable a element has no role, aria-haspopup, or aria-expanded.

The submenu is marked up with role="menubar", but a nested pop-up submenu should use role="menu", not "menubar" (which is reserved for a permanently visible top-level bar). The submenu items "Persvragen" and "Data en API" also have role="menuitem" and the attributes aria-haspopup and aria-expanded on a non-focusable li element. Moreover, these attributes (aria-haspopup and aria-expanded) are used incorrectly, because these submenu items do not actually expand anything.

As a result, assistive technology may not expose the correct role and expanded/collapsed state on the elements that receive focus, and may announce pop-ups and expanded states that do not exist. Screen reader users may hear the links "Over ons", "Persvragen", and "Data en API", but may not be correctly informed which items open a submenu or whether a submenu is expanded or collapsed.

User story

As a visitor, I use a screen reader. When I navigate to a menu item that opens a submenu, I expect the focused element to clearly announce that it has a submenu and whether it is expanded or collapsed, and I expect items without a submenu not to claim they have one. Without accurate information, I do not understand how the menu behaves or what happens when I activate it.

How to test

Navigate through the main menu with a keyboard and screen reader. Move the focus to "Over ons" and then to the submenu items "Persvragen" and "Data en API". Check whether each focused element is announced with the correct role and, where applicable, with an accurate expanded/collapsed state. Inspect the accessibility tree and confirm that aria-haspopup and aria-expanded are on the focusable interactive elements (not only on non-focusable li containers), that aria-haspopup and aria-expanded are present only on items that actually control a submenu, and that the submenu container uses an appropriate role.

Solution

Place the interactive role and states on the focusable element that controls the submenu. For example, give aria-haspopup="true" and aria-expanded to the a element of "Over ons" and update aria-expanded dynamically when the submenu opens or closes. Keep the li elements as structural containers (for example, with role="none"). Change the submenu container from role="menubar" to role="menu". Remove aria-haspopup and aria-expanded from the submenu items "Persvragen" and "Data en API", because they do not control a further submenu. Make sure the submenu uses a valid and consistent navigation/menu pattern: https://www.w3.org/WAI/ARIA/apg/patterns/menubar/.

The current implementation tries to use the ARIA menu/menubar pattern, but the required roles, states, and interactions are not implemented correctly. The best approach is to use a standard navigation pattern with native HTML elements. Navigation items that go to another page should be links (a elements). Items that open or close a submenu should be buttons (button elements). If "Over ons" both navigates to a page and gives access to a submenu, use separate controls: a link for navigation and a button for expanding and collapsing the submenu. The submenu should be a nested list of links. Submenu items like "Persvragen" and "Data en API" remain simple links, because they do not open a further submenu.

The example below is illustrative. When the submenu opens, remove the hidden attribute and set the button to aria-expanded="true". When it closes, add hidden again and set aria-expanded="false".

<li class="top-level menu-item has-children">
  <!-- The page link stays a real link -->
  <a href="/over-ons/">Over ons</a>

  <!-- A real button toggles the submenu -->
  <button
      type="button"
      aria-expanded="false"
      aria-controls="submenu-over-ons"
      aria-label="Submenu Over ons">
    <!-- Decorative icon: hidden from screen readers -->
    <svg width="16" height="16" viewBox="0 0 24 24" aria-hidden="true" focusable="false">
      <path d="M6 9l6 6 6-6" fill="none" stroke="currentColor" stroke-width="2"/>
    </svg>
  </button>

  <!-- Submenu is hidden until expanded -->
  <ul id="submenu-over-ons" hidden>
    <li><a href="/persvragen/">Persvragen</a></li>
    <li><a href="/data-en-api/">Data en API</a></li>
  </ul>
</li>

#6 - Submenu is not accessible with the keyboard

Impact: High Type: Technical WCAG: 2.1.1 EN: 9.2.1.1

The main menu in the header of this website contains a submenu that opens with "Over ons" and cannot be operated with the keyboard. Submenus must be fully keyboard accessible. Visitors must be able to open, move through, and select items in submenus using the keyboard alone. In addition, the information in these submenus must be accessible to all visitors, regardless of whether they use a mouse or keyboard. Finally, the pages the submenu items link to should contain all the information found in the submenus themselves. Information must not be available exclusively within the submenu.

User story

As a visitor, I use the website with a keyboard. When I navigate through the menu, I cannot open the submenus with my keyboard. I expect to be able to reach and use all submenu items without a mouse.

How to test

Disconnect the mouse and move through the page with Tab, Enter, Space, and the arrow keys. Every link, button, form field, and custom component must be reachable and operable. Watch for onclick handlers without a keyboard equivalent and interactions that only work by dragging.

Solution

Make sure all submenus are fully operable with the keyboard. Visitors must be able to open submenus with Enter or Space on the parent menu item, navigate within them with Tab or the arrow keys, and close them with Escape. All information and links in the submenus must be reachable through keyboard navigation. In addition, the pages the main navigation items link to should contain the same information as the submenus, so that no content is available exclusively through the submenu.

#7 - Empty navigation landmark is exposed to assistive technology

Impact: Low Type: Technical WCAG: 1.3.1 EN: 9.1.3.1

In the header there is a nav element with the accessible name "Mobile Main menu". On large (desktop) viewports, the menu content is hidden with CSS (display: none), making all links and menu items inaccessible to screen reader users. The nav element itself, however, remains exposed to assistive technology.

As a result, screen readers announce a navigation landmark named "Mobile Main menu", even though it contains no perceivable or operable content. This creates an empty navigation area and exposes a page structure that does not match what is shown visually.

Screen reader users who navigate by landmarks may go to the "Mobile Main menu" area and find no content there, which is confusing and makes navigation less efficient.

User story

As a visitor, I use a screen reader and often navigate by landmarks. When I go to a navigation area, I expect usable navigation content there. A navigation area labeled "Mobile Main menu" that is empty makes me think the content has not loaded or that I missed something, and makes the page structure harder to understand.

How to test

Inspect the page at a desktop-width viewport with the browser's developer tools and a screen reader. Check whether a navigation landmark named "Mobile Main menu" is present. Check whether that landmark contains exposed, operable content; if the content container is display: none while the nav wrapper remains exposed, the landmark is empty. Confirm that hidden mobile navigation areas are not exposed to assistive technology when their content is not available.

Solution

Make sure the navigation landmark is only exposed when it actually contains usable content. If the mobile menu's content is hidden at desktop width, also hide the enclosing nav element from assistive technology, for example by applying display: none to the nav element itself instead of only to the inner container. That way the empty landmark is removed from the accessibility tree and the exposed structure matches the content that is actually present.

#8 - Custom keyboard focus indicator has insufficient color contrast

Impact: High Type: Technical WCAG: 1.4.11 EN: 9.1.4.11

At the bottom of the website's pages there is a sticky button that opens a cookie settings widget. This button has a custom keyboard focus that looks like a dark blue (#1032CF) border on a blue (#005EA5) background. The contrast ratio between these colors is 1.3:1, which is below the required minimum of 3.0:1. Custom keyboard focus indicators must meet the contrast requirements, unlike the default browser focus indicator. Because visitors cannot adjust custom focus indicators, they must have a contrast ratio of at least 3.0:1 with the background.

User story

As a visitor with a visual impairment, I use the website with a keyboard. When I navigate through the page, I cannot clearly see which element has focus. I expect the focus indicator to stand out clearly against the background.

How to test

Measure the contrast of focus indicators, input field borders, checkbox and radio button states, and informative icons against their background with the Colour Contrast Analyser. The lower limit is 3.0:1. Do not forget chart segments and link underlines.

Solution

Increase the contrast of the custom focus indicator so that it meets this requirement.

#9 - Visible text on the images is not in the text alternative

Impact: High Type: Content WCAG: 1.1.1, 2.5.3 EN: 9.1.1.1, 9.2.5.3

In the footer, the images under "Download de zwemwater app" show the full text "Download in de App Store" and "Ontdek het op Google Play". The text alternatives (the alt texts), however, are "Download op de App Store" and "Download op Google Play". The alt text should contain all visible text, so that visitors who cannot see the image receive the same information.

This difference also prevents these images (which are also links) from being activated with voice control. When the visible text differs from the accessible name, voice commands based on the visible text do not work.

User story

As a visitor, I read the website with a screen reader. When I navigate to the image with text, I do not hear the full text shown on the image. I expect the text I hear to match what is shown visually on the image. I also use the website with voice input. When I speak the visible link text, the website does not recognize my command and nothing happens. I expect the link to open when I speak the visible text.

How to test

Inspect images that contain visible text and check whether their text alternatives or accessible names contain all the text shown on the image. Compare the visible text with the accessible name exposed to assistive technology. Also check whether linked images can be activated with voice control commands based on the visible text.

Solution

Update the text alternatives so that they contain the full visible text on the images. For example: "Download in de App Store" and "Ontdek het op Google Play". Make sure the accessible name of each linked image contains the same text that is shown visually.

In the footer, the text "Download de zwemwater app" is not marked up as a heading. #11 - The button's name does not describe what the button does

Impact: High Type: Technical WCAG: 2.4.6 EN: 9.2.4.6

When the website's pages are viewed on a small screen, the header contains the button "Menu" that opens the navigation menu. After the visitor opens the navigation menu and closes it again, the accessible name of this button is "Sluit menu", which does not describe its function. This makes it difficult for blind visitors and visitors who rely on screen readers to understand the purpose of the button. The accessible name should convey the button's action clearly and concisely.

User story

As a visitor, I read the website with a screen reader. When I come across a button, I hear a name that does not tell me what the button does. I expect every button to have a clear name that describes the action.

How to test

Make a list of all headings (use HeadingsMap or a screen reader's heading list) and all form labels. Each must describe clearly enough what follows it to make a navigation choice. Vague headings like "Section" or "More info" do not help; neither do identical labels for different fields.

Solution

Update the accessible name so that it accurately conveys the button's function (for example, "Open menu").

#12 - Incorrect ARIA roles and structure in the navigation menu

Impact: High Type: Technical WCAG: 1.3.1, 4.1.2 EN: 9.1.3.1, 9.4.1.2

When the website is viewed on a small screen, the "Menu" button in the header opens the navigation menu. The navigation menu, however, is built with ARIA roles that do not accurately reflect its purpose and structure.

The navigation is exposed as a tree widget with role="tree" and role="treeitem", while it functions as a website's navigation menu. Tree widgets are intended for hierarchical application controls and require specific interaction patterns that differ from standard website navigation.

In addition, interactive roles and states such as role="treeitem", aria-haspopup, and aria-expanded are applied to non-focusable li elements instead of to the focusable controls that visitors interact with. As a result, assistive technology may not expose the correct role, purpose, or state of menu items.

The submenu structure that opens with "Over ons" also contains a mix of different ARIA roles, including treeitem, menuitem, and group, which produces an inconsistent accessibility structure that assistive technology may interpret differently.

Moreover, the text "Menu" in the navigation menu is exposed as a treeitem, while it is a section title and not an interactive menu item. As a result, screen reader users come across elements that are announced as interactive even though they cannot be activated.

As a result, assistive technology receives an inaccurate representation of the menu structure, the roles, and the relationships. Screen reader users may have trouble understanding the menu, recognizing interactive elements, and moving through the submenu hierarchy.

User story

As a visitor, I use a screen reader to navigate the website. When I enter a navigation menu, I expect menu items, submenu buttons, and their states to be announced consistently and accurately. I rely on correct roles and relationships to understand which elements are interactive and how the menu is built.

How to test

Navigate through the menu with a screen reader and inspect the accessibility information exposed for each menu item. Check whether navigation menus use appropriate navigation semantics, whether interactive roles and states are on the focusable controls, and whether non-interactive elements are not announced as interactive. Check whether the accessibility structure is consistent throughout the menu hierarchy.

Solution

Remove role="tree" and role="treeitem". Use a standard website navigation pattern instead of an ARIA tree widget. The menu should be built as ordinary navigation with lists and links, and only submenu buttons should be exposed as buttons. Place aria-expanded and aria-controls on the focusable button, not on the li element. Expose "Menu" as a heading, not as a menu item. Keep the role structure consistent throughout the menu. For example:

<nav aria-label="Mobile main menu">
  <h2>Menu</h2>

  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/veilig-zwemmen/">Veilig zwemmen</a></li>
    <li><a href="/gezondheidsrisicos/">Gezondheidsrisico's</a></li>
    <li><a href="/schoon-water/">Schoon water</a></li>

    <li>
      <button
        type="button"
        aria-expanded="false"
        aria-controls="submenu-over-ons">
        Over ons
      </button>

      <ul id="submenu-over-ons" hidden>
        <li>
          <button
            type="button"
            aria-label="Terug naar hoofdmenu">
            Terug
          </button>
        </li>
        <li><a href="/over-ons/">Over ons</a></li>
        <li><a href="/persvragen/">Persvragen</a></li>
        <li><a href="/data-en-api/">Data en API</a></li>
      </ul>
    </li>

    <li><a href="/nieuws/">Nieuws</a></li>
    <li><a href="/vragen-of-klachten/">Vragen of klachten?</a></li>
  </ul>
</nav>

Update aria-expanded dynamically when the submenu opens or closes and remove the hidden attribute when the submenu becomes visible.

#14 - The relationship between breadcrumb items is not captured in the code

Impact: Medium Type: Technical WCAG: 1.3.1 EN: 9.1.3.1

On the pages, the items in the breadcrumb are visually grouped, but this grouping is not present in the HTML structure. When elements are visually grouped, this relationship should also be present in the HTML, so that visitors with assistive technology such as screen readers understand the grouping.

User story

As a visitor, I use a screen reader to navigate the website. When I come across a breadcrumb, I expect the links to be announced as a single navigation path rather than as separate links. That way I understand where I am on the website and how the current page relates to other pages.

How to test

Navigate with a screen reader to the breadcrumb and inspect the HTML structure. Check whether the breadcrumb items are semantically grouped and exposed as a single navigation component. Check whether assistive technology can recognize the breadcrumb as a navigation path and whether the relationship between the items is conveyed programmatically.

Solution

Group the breadcrumb items with appropriate semantic markup. For example, place the breadcrumb in a navigation landmark and use a list structure to reflect the relationship between the items. That way assistive technology recognizes the breadcrumb as a single navigation structure and the relationship between the items is conveyed. For example:

<nav aria-label="Breadcrumb">
  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/section">Section</a></li>
    <li aria-current="page">Current page</li>
  </ul>
</nav>

#15 - Focus is lost after the search results are updated

Impact: High Type: Technical WCAG: 2.4.3 EN: 9.2.4.3

This page contains a search field under "Search by swimming spot or place name" that automatically updates the search results as the visitor types. When a search term changes the results, the keyboard focus is lost. As a result, keyboard and screen reader users lose their place on the page and have to navigate back to the search field or the results to continue. Because this only happens when the results actually change, the problem can seem inconsistent and hard to predict.

When content is updated automatically, the keyboard focus should stay on the current control or move to a logical place, so that visitors can continue their interaction without interruption.

The same problem occurs on the page https://www.zwemwater.nl/nieuws/.

User story

As a visitor, I use the website with a keyboard or a screen reader. When I type a search term into a search field and the results are updated automatically, I expect to stay in the search field, so that I can keep typing or review the results. When the focus is lost, I lose my place and have to start navigating over again.

How to test

Navigate to the search field using only the keyboard. Enter a search term that changes the search results. Check whether the focus stays on the search field after the results are updated. Repeat this with different search terms that produce different results.

Solution

Make sure the keyboard focus stays on the search field when the results are updated automatically. Visitors should be able to keep typing and interact with the updated results without losing their place on the page.

#17 - Status message is not announced by screen readers

Impact: High Type: Technical WCAG: 4.1.3 EN: 9.4.1.3

This page contains a search feature that automatically updates the results as the visitor types. When a search returns no results, the message "Unfortunately, no results found" appears on the screen. However, this message is not announced automatically by screen readers. Although the search result area is marked as a live region, changes to the content are not reliably announced by screen readers. As a result, screen reader users may not notice that the search has completed and that no results were found. Visitors have to navigate through the page manually to discover that the results have changed.

Status messages that appear dynamically should be announced automatically without visitors having to move the focus to the message.

User story

As a visitor, I use a screen reader to find information on the website. When my search returns no results, I expect to be informed about that automatically. Otherwise I might think the search is still loading or that there are results elsewhere on the page.

How to test

Using a screen reader, perform a search that returns no results. Check whether the message "Unfortunately, no results found" is announced automatically when it appears. Visitors should not have to move the focus or navigate to the message to discover that the search returned no results.

Solution

Make sure status messages are announced automatically by assistive technology. For more details, see, for example, the page: https://www.w3.org/WAI/WCAG21/Techniques/aria/ARIA22.

This page contains an iframe without a title attribute under the heading "4. Ga goed voorbereid het water op". Iframes need descriptive titles, usually via the title attribute. This title should describe the type of content in the iframe with a unique and meaningful description. This text helps blind visitors decide whether it is worth exploring the content of the iframe.

User story

As a visitor, I use the website with a screen reader. When I come across an embedded frame, I need to understand what content it contains before I decide whether to enter it. If the iframe has no title, I cannot determine its purpose and may miss important information or waste time on irrelevant content. I expect every iframe to have a clear and descriptive title.

How to test

Inspect all iframes on the page with the browser's developer tools or accessibility inspection tools. Check whether each iframe has a title attribute that clearly describes the content or purpose of the embedded resource. Test with a screen reader and confirm that the iframe is announced with a meaningful description, so visitors understand what it contains before entering it.

Solution

Add the title attribute to the iframe element and put text in it that shows which type of content the iframe contains and what the content is about.

#41 - Visual information in the video is not accessible

Impact: Medium Type: Content WCAG: 1.2.3, 1.2.5 EN: 9.1.2.3, 9.1.2.5

On this page, under the heading "4. Ga goed voorbereid het water op", there is a video. The video contains text and logos at various moments (for example around 0:08 and 0:32). However, there is no media alternative or audio description. This video contains visual information (text and logos) that is inaccessible to blind visitors.

User story

As a visitor, I read the website with a screen reader. When I watch a video with logos or text on screen, I miss that information entirely. I expect an audio description or a written alternative that includes those visual details.

How to test

Determine for each video whether there is visual information that is not in the audio (text on screen, demonstrations, actions). If so, look for an audio description track or a text alternative with all spoken and visual information, placed near the video.

Solution

Previously, a media alternative (a textual representation of all information) was an acceptable solution, but success criterion 1.2.5 now requires an audio description of the visual content for such videos. An audio description must therefore be added to make this video accessible.

#42 - Automatically generated captions

Impact: Medium Type: Content WCAG: 1.2.2 EN: 9.1.2.2

This page contains a video with a voice-over under the heading "4. Ga goed voorbereid het water op". There are captions, but they are automatically generated and therefore inaccurate. Videos with spoken content need accurate captions to be accessible to visitors with a hearing impairment. These captions must match the spoken words in the video exactly. Because the automatically generated captions contain errors and misinterpretations of the spoken word, they do not meet this accessibility requirement.

User story

As a deaf or hard-of-hearing visitor, I watch a video. The automatic captions contain errors and lack punctuation, which makes them unreliable. I expect the captions to match exactly what is being said.

How to test

Look for each prerecorded video with sound and turn on captions in the player. For each video, watch a few minutes and check whether the captions cover all spoken text and important sounds, in the same language as the speech. Check whether the CC button is reachable with keyboard and screen reader.

Solution

Make sure the captions are high quality and accurately represent what is said in the video.

#43 - Single-character keyboard shortcuts are present

Impact: Medium Type: Technical WCAG: 2.1.4 EN: 9.2.1.4

This page contains a YouTube video player under the heading "4. Ga goed voorbereid het water op" that uses single-character keyboard shortcuts, such as 'k' to play or pause the video and 'm' to mute the sound. These shortcuts conflict with screen readers, because they are also active when keyboard focus is on another element in the video player. This can cause problems for visitors who use speech recognition, because these letters can occur in spoken words. It can also be annoying for visitors who accidentally press a key.

User story

As a visitor, I use the website with speech input. When I say a word with a 'k' or 'm', the video unexpectedly pauses or mutes. I expect single letters not to trigger actions outside the video player.

How to test

Look up the documentation for the keyboard shortcuts. Every single-character shortcut (such as J, ?, /) must be able to be turned off, be remappable to a combination with a modifier key (Ctrl/Alt/Cmd), or only be active when the relevant component has focus. Test by activating speech input.

Solution

You can solve this by adding the parameter disablekb=1 to the video URI in the HTML code. This disables the keyboard shortcuts while keyboard operation remains possible. For more information, see https://developers.google.com/youtube/player_parameters#disablekb.

#44 - em used only for visual emphasis

Impact: Low Type: Content WCAG: 1.3.1 EN: 9.1.3.1

On this page, the em element is used purely to make text stand out visually, while the content itself does not require emphasis. See the text in the section that opens with "Wat is het verschil tussen de 'Waterkwaliteit in de laatste vier jaar' en de 'actuele zwemwaterkwaliteit' van een zwemlocatie?". The em element means "emphasis in speech". Screen readers often change their tone for these elements. When they are used for styling instead of meaning, random words sound emphasized and the spoken text takes on a meaning the author did not intend.

User story

As a visitor, I read the website with a screen reader. When I listen to a text, random words suddenly sound emphasized when that was not intended. I expect only genuinely important words to receive extra emphasis.

How to test

Go through the page with DevTools and a screen reader. Visual headings, lists, tables, fieldsets, and active states must all exist in the HTML, not only as styled text. Use axe for a quick automated scan and then check whether the structure makes sense when a screen reader reads it out linearly.

Solution

Use the em element only when a word or phrase is genuinely important, or would be emphasized in speech. Use CSS to make text stand out visually only, for example a custom class attribute with font-weight: bold or font-style: italic.

About this study

Reading guide

Our reports are different. When discussing the problems we found, we do not follow the structure of the standard, but that of your website or app. This way you can simply get to work page by page or screen by screen. Much easier! Further on you will find an overview of all pages with problems.

For each issue we found we give you a few examples, but not a complete list. Check for yourself whether the problem also occurs in other places. See the report as a guide.

Standard used

This study shows to what extent the website currently meets WCAG 2.2, level A and AA. WCAG stands for Web Content Accessibility Guidelines. This is the international standard for digital accessibility. The European standard EN 301 549 contains all requirements of WCAG at level A and AA.

In this report we have included short descriptions of the success criteria from the standard, with a general explanation. Do you want to read them in full? Then take a look at the WCAG documentation.

Research method used

We use the WCAG-EM research method from the W3C. The process looks like this:

  • determine what falls inside and outside the scope
  • determine which technologies have been used
  • compile a sample
  • examine the sample
  • describe the issues found

We do the largest part of the research by hand. For some of the accessibility requirements we use automated tools as support, such as axe-core and Chrome Developer Tools.

Important to know

This report helps you improve the accessibility of your website. But please note: it is not a definitive, complete list of all accessibility problems present. Here is why:

It is a sample

First, the research is based on a sample. It was taken in a reliable way, and most problems will therefore certainly come to light. Still, a problem may fall just outside the sample. In a follow-up study it may well be discovered.

Based on falsification

We assess from the principle of falsification. That means we try to prove that something is not true, instead of confirming that it is correct. ‘Meets’ therefore means that we found no reason to reject a point. But if we do find a reason later, it can still be rejected.

Evolving insight

It happens that the assessment of a success criterion changes at the detail level. The standard does not describe every possible scenario. Together with other research agencies we discuss how we handle certain situations. So something that is rejected now may sometimes be approved in a follow-up study, and the other way around.

Solving leads to a new problem

Finally, it can happen that solving a problem unintentionally creates a new accessibility problem. That only comes to light in a follow-up study.

How does this report work?

Viewing and filtering findings

All accessibility problems found are listed under Problems found. You can filter the findings by:

  • Impact (High, Medium, Low, Advice) — how serious is the problem for the user?
  • Type (Content, Technical) — does the content or the technology need to be adjusted?
  • Status (Open, Solved) — which problems have already been resolved?

Tracking progress

You can track your progress in two ways:

  • CSV export — export all findings as a CSV file and load it into an (online) spreadsheet to collaborate with your team.
  • Jira export — export all findings as a Jira-compatible CSV file. Import it via Jira > Issues > Import issues from CSV. Findings are created as bugs with priority based on impact.
  • Register in the browser — enable this option to track per finding whether it has been solved. Your progress is saved in your browser. No one else can see your result. Note: the progress is tied to your browser. If you use a different browser or device, the count starts over.
  • Action plan — download a prioritized action plan to solve the problems found step by step. This is available for audits from March 2026 onward.

Sharing a link to a specific finding

For each finding a link icon appears when you hover over it with the mouse. Click this icon to copy the direct link to that finding. You can paste this link into an email or chat message, for example to ask Proper Access a question about a specific point.
